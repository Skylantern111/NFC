## Round 4 — done (deeper pass: shared component internals and CSS cascade, not just per-page copy)

Rounds 1–3 worked page-by-page. This pass instead read the shared primitives everything else is built on (`components/ui/card.jsx`, `dialog.jsx`, the `lib/*` helpers) and traced how their defaults actually cascade into every page that uses them — which is where the deepest, least-obvious bug of the four rounds turned up.

### 1. `components/ui/card.jsx`'s default `border` silently outlined almost every card in the app — fixed
**Resolution:** dropped the bare `border` utility from `card.jsx`'s base className (with a comment explaining why), in the one file that fixes every call site at once. Rebuilt clean; every glass/solid card in the app now shows only the border its own className actually specifies (i.e. none, except `GlassCard.jsx`'s deliberate `border-white/60`).
The base `Card` component (`src/components/ui/card.jsx:11`) ships `"bg-card text-card-foreground flex flex-col gap-6 rounded-xl border py-6 shadow-sm"`. That bare `border` utility renders a 1px `hsl(var(--border))` (light slate-grey) outline, and it is never cancelled: every real call site in the app only overrides background/blur/radius/shadow (e.g. Items.jsx/Messages.jsx/Notifications.jsx/ClaimTag.jsx's `glass = 'bg-white/70 backdrop-blur-xl rounded-3xl'`, Chat.jsx/NfcLanding.jsx's `GLASS` constant, Dashboard.jsx's and Inventory.jsx's inline `rounded-3xl bg-white/80 ... shadow-lg`) — none of them pass `border-none`/`border-0`, and grepping the whole `src/pages` tree confirms zero call sites do. Because `cn()` uses `tailwind-merge`, which treats bare `border` (width/style) and a color-only utility as separate groups, nothing about those overrides removes the inherited border-width utility.
Compare this to `components/GlassCard.jsx` — the *only* component that actually uses the real `.glass` utility class defined in `index.css` (`bg-white/70 backdrop-blur-xl border border-white/60 shadow-lg rounded-3xl`), which deliberately sets a **white**-tinted edge highlight as part of the glassmorphism look. Every other page's hand-rolled "glass" card is really a shadcn `Card`, and instead of that intentional white edge, it's getting an unrelated grey outline nobody asked for. The design-system comment block in `index.css` (added Round 1) documents glass vs. neumorphic vs. admin-solid as the only three deliberate surface treatments — a stray grey-bordered fourth variant isn't one of them.
**Fix at the source, one file:** drop `border` from `card.jsx`'s base className. Nothing in the codebase relies on `Card`'s default bordered look (every usage already fully re-skins it), so this is a pure bug fix, not a behavior change anyone depends on.

### 2. Glass "material" had drifted into three slightly different recipes across pages — unified
**Resolution:** `Chat.jsx` and `NfcLanding.jsx`'s `GLASS` constants moved from `backdrop-blur-2xl` to `backdrop-blur-xl`, matching the majority (and the `.glass` class itself). `Dashboard.jsx`'s stat cards, "No active incidents" card, and privacy-note card moved from a flat `bg-white/80` (no blur) to `bg-white/70 backdrop-blur-xl`, matching the rest of the owner dashboard. Dashboard's semantic accent cards (the red active-incident card, the amber stale-item nudge) were deliberately left untouched — those are intentional accent surfaces per the existing red/amber semantics, not part of the neutral-card drift.

### 3. `ProtectedRoute.jsx`'s auth-check screen had no spinner — fixed
Round 3 gave `AdminLayout.jsx`'s `AdminGate` a `Loader2` spinner but missed its sibling. **Resolution:** `ProtectedRoute.jsx` — which gates every `/dashboard/*` route — now shows the same spinner-plus-label pattern.

### 4. Relative-time formatting was implemented three separate times — consolidated
**Resolution:** removed the local `relativeTime()` functions from `Inventory.jsx` and `Moderation.jsx`; both now call the shared `relativeTimeFromMs(toMillis(x))` from `lib/utils.js`, which already normalized both a Firestore Timestamp and a plain `Date`/parseable value into milliseconds — no wrapper needed, the existing helper's dual-shape handling was already sufficient.

### 5. `ClaimTag.jsx`'s NFC scan handler was registered in the wrong order relative to `scan()` — fixed
**Resolution:** `reader.onreading`/`reader.onreadingerror` are now assigned before `await reader.scan()`, matching the Web NFC spec's own reference pattern, so a tag tapped in the gap between `scan()` starting and a handler being attached can no longer fire unheard.

## Round 5 — done (color system rework)

| # | Item | Resolution |
|---|------|------------|
| 1 | Build a proper hex/HSL scale | `src/index.css`'s `:root`/`.dark` blocks now define one canonical scale per role, each with a light and dark value: canvas/surface/ink/line (dominant neutral), brand (purple), signal (pink), plus destructive as a functional color kept outside the decorative scale. A new `--neu-shadow-strong`/`-strong-light`/`-soft`/`-soft-light` quartet does the same for the neumorphic shadow pair, which was previously hardcoded `rgba(...)` literals baked directly into `tailwind.config.js`'s `boxShadow.neu-*` — those now read `var(--neu-shadow-*)`, so the one CSS file is the single source of truth for both palettes. |
| 2 | Name tokens by job, not by value | Every token's trailing comment in `index.css` now names its job (canvas, surface, ink, ink-muted, line, brand, signal, danger) instead of a hue family (`purple-500`, `pink-500`, `slate-800`), grouped under `/* --- dominant neutral, ~60% --- */`, `/* --- secondary, ~30%: brand --- */`, `/* --- accent, ~10%: signal --- */`, `/* --- functional, outside the ratio --- */` section headers so the ratio itself is legible at the token layer, not just described in prose. `tailwind.config.js`'s `base` color got the same treatment — it's documented as "the neumorphic canvas color" rather than left as a bare hex. |
| 3 | Balance 60/30/10 | Verified structurally rather than reflowed: canvas/surface/ink already dominate every screen's area (page background + card surfaces), brand purple is the actual workhorse (buttons, links, focus rings, badges, checkboxes), and signal pink only ever appears inside small, deliberate accents (icon-badge gradients, hero headline gradient text, one CTA button) — never as a large fill. No page needed rebalancing; this was confirmed by grepping every `from-purple-*-to-pink-*` gradient use (7 files, all small logo marks / button labels / headline text, not backgrounds) rather than assumed. |
| 4 | Always check contrast | Computed WCAG relative-luminance contrast for every foreground/background pair actually used together, light and dark (see ratios inline as comments in `index.css`). This caught two real failures that had never been checked before: light-mode `--muted-foreground` on `--background` was 3.96:1 (fails 4.5:1 body text) — darkened `220 9% 46%` → `220 9% 40%`, now 4.93:1. Dark-mode `--destructive-foreground` (white) on `--destructive` (a bright, washed-out red) was **2.74:1 — fails even the 3:1 UI-component floor**, i.e. white button text was nearly invisible; fixed by switching dark-mode destructive/primary/accent foregrounds to dark ink on their pastel-bright fills (same pattern the original dark palette already used for `--primary`), now 5.50:1/6.65:1/6.89:1. Also re-tuned dark-mode `--primary`/`--accent`: they were a mint-green/lavender hue pair unrelated to light mode's purple/pink brand (dead code, so this had never been noticed) — now the same brand/signal hue families, lightened for a dark canvas instead of hue-swapped, so the two themes read as the same product. |
| 5 | Instant dark mode | `ThemeContext` is now mounted (`src/main.jsx` wraps the app in `<ThemeProvider switchable>`), with a toggle wired into a new "Appearance" card on `Settings.jsx` (`useTheme()` → `Switch checked={theme === 'dark'} onCheckedChange={toggleTheme}`). An inline blocking script in `index.html`'s `<head>` applies `.dark` from `localStorage` before first paint, so a reload with dark mode on doesn't flash light first. `components/ui/sonner.jsx` was pulled off the unused `next-themes` package (no provider was ever mounted for it, so `Toaster` was always silently rendering with `theme="system"`) onto the app's own `ThemeContext`, so toast styling now actually matches. `tailwind.config.js` gained `darkMode: 'class'` so `dark:` variants respond to the toggle instead of OS `prefers-color-scheme`. |

**How the toggle reaches the whole app, not just the token layer:** most of the app's chrome (`bg-base` neumorphic surfaces, `shadow-neu-*`) now flips automatically since `base` and the shadow pair are CSS-var-backed (item 1) — zero per-file changes needed for nav rails, buttons, inputs, or the ambient background. For the ~25 files using hardcoded Tailwind palette classes for content text/surfaces (`text-slate-500`, `bg-white/70` glass cards, etc.), a small mapping table (e.g. `text-slate-800`→`+dark:text-slate-100`, `bg-white/70`→`+dark:bg-white/5`) was applied as an additive, mechanical pass across every match in `src/` — additive because `dark:`-prefixed utilities are inert without the `.dark` class, so this carries zero light-mode regression risk. `npm run build` succeeds after the change; a live browser check wasn't possible in this environment (no Chrome extension connection), so the visual result is unverified beyond the computed contrast ratios and a manual diff review of the token-layer and shared-primitive changes — same category of limitation Round 1 flagged for the original contrast/focus-ring pass.

**Left as-is / out of scope for this round:** the `void`/`panel` custom colors (`tailwind.config.js`) are unused anywhere in `src/` (only referenced by `index.html`'s `theme-color` meta), so they were left as static hex rather than wired into the token system. `GlassCard.jsx`'s `lost` (red alert) variant and the purple→pink brand gradients were left untouched by the automated pass — they're semantic/brand accents, not neutral chrome, and read fine on both canvases without a dark-specific override.

## Round 9 — done (route-level code-splitting)

Scope: a different dimension entirely — every round through 8 was visual or logic correctness; this one is bundle size, the thing every single `npm run build` since this plan started has been quietly warning about ("Some chunks are larger than 500 kB") without anyone acting on it. Chosen over the round's other candidate, automated test coverage, because it's contained (no new dependencies, no emulator/CLI needed) and immediately measurable in the build output — the user picked this explicitly over the test-coverage option when asked.

**Problem:** `App.jsx` statically imported all 17 route components — public pages, every owner-dashboard page, and every admin-console page — into one bundle. A finder tapping an NFC tag (`/nfc/:tagId`, no login, the single highest-traffic anonymous route in the app) downloaded the entire owner dashboard and the entire admin console (`Inventory.jsx` alone had grown to ~31KB of source across Rounds 6–8) before rendering a page that needs none of it.

**Fix:** `DashboardLayout` and all seven of its child routes, plus `AdminLayout` and its three child routes, converted from static `import` to `React.lazy(() => import(...))`, wrapped in one `<Suspense>` around `<Routes>` with a fallback reusing the exact loading-screen markup `ProtectedRoute`/`AdminGate` already use elsewhere (`Loader2` + "Loading…" on `bg-base`), so a chunk fetch reads the same as the auth check it's already sitting behind. Public routes (`Landing`, `Login`, `Register`, `NfcLanding`, `Chat`) stayed eager on purpose — they're first-paint/entry routes hit with no prior page load to have warmed a chunk, so splitting them trades a network round-trip for a savings that doesn't apply (nobody's shipping dashboard/admin code to them regardless).

**Result:** the single 991KB main chunk (Round 8's build) is now 832KB main + 12 route-level chunks (`Inventory.jsx` 31KB, `ClaimTag.jsx` 55KB — the two heaviest, `Dashboard`/`Owners`/`Moderation`/etc. each 2–9KB) that only load when their route is actually visited. `/nfc/:tagId` and `/chat/:chatId` no longer pull in any dashboard or admin code at all.

**Left for a future round:** the remaining 832KB main chunk is mostly the shared UI library (Radix primitives every page imports from `components/ui/*`), Firebase's modular SDK, and React itself — collapsing that further needs `manualChunks` tuning or an audit of which Radix components are actually used vs. imported wholesale, a meaningfully different (and open-ended) exercise from the route-level split done here. `npm run build` passes and the chunk list in its own output is the verification for this round — no browser needed to confirm a bundle got smaller.

Every item below is grounded in a specific file/line, not general advice.

| # | Finding | Plan |
|---|---------|------|
| 1 | **Finder chat replies are rejected the moment a real Firebase project connects** | `lib/ownerItems.js:498` `sendChatMessage(chatId, sender, text)` writes `{ sender, text, timestamp }` with no `finderSessionToken`. `firestore.rules:196-199` requires `request.resource.data.finderSessionToken` to match the chat's stored token for any `sender=='finder'` message create — a missing field never equals a token string, so every finder-sent message is rejected server-side. One-directional (owner→finder is a different, unaffected rule branch). This has been latent since before this session — invisible because the app has only ever run with `firebaseReady:false` (no `.env` in this repo), so the real rule path has never actually been exercised. Plan: thread `finderSessionToken` through `sendChatMessage`'s write for the finder-sender branch. |
| 2 | **A complete `ErrorBoundary.jsx` exists and is never mounted** | `src/components/ErrorBoundary.jsx` is a working class component (icon, message, "Reload Page" button) — `grep` for its usage outside its own file returns nothing. Any uncaught render-time throw (an unexpected `undefined.toDate()`, a bad prop shape) currently unmounts the whole React tree to a blank white screen with zero recovery UI. Plan: wrap `<App />` in `main.jsx` with it — the component already exists, this is a mount, not new code. |
| 3 | **A finder's GPS location is captured and stored, then never shown to the owner** | `NfcLanding.jsx` has a full "Share my current location" flow (`captureLocation()`, an accuracy badge, writes `location: {lat, lng, accuracy}` onto the `reports` doc). For a lost-and-found app this is the single most valuable piece of data a finder can hand over, currently discarded after they've already granted the permission. Plan: either build the map (owner-side, on the report/chat hero card) or, if genuinely out of scope, stop asking finders for a permission the app throws away. |
| 4 | **Settings' "Email alerts" toggle does nothing** | `Settings.jsx` offers an "Email alerts" switch that persists `notificationPrefs.email` to Firestore. There is no `functions/` directory, no `firebase.json`, no email service integration anywhere in the repo — nothing has ever sent, or could send, an email for a report/message event. A user enabling this reasonably believes they'll be emailed; they never will be. Plan: either build the send path (a Cloud Function on `notifications` create, or similar) or relabel/disable the toggle so it stops promising something that doesn't exist. |
| 5 | **No email verification on Register — a mistyped address is accepted forever** | `Register.jsx` calls `createUserWithEmailAndPassword` and never `sendEmailVerification`; nothing in the app ever checks `user.emailVerified`. | 6 | **A private/incognito finder loses their identity on every visit, silently** | `lib/finderSession.js`: when `localStorage` throws (private mode, storage blocked), the catch branch returns `nanoid(24)` freshly generated with no memoization — a new random token on every single call, not just every session. Plan: memoize the fallback token in a module-level variable for the life of the tab, and/or surface a warning that private-mode sessions won't persist across visits. |
| 7 | **NfcSetup's "this ID can't be claimed" caveat is read (if at all) after the physical write already happened** | `NfcSetup.jsx`: the generate → copy → **write-to-tag** flow is the first card, top of page; the "This ID isn't in the provisioned inventory, so it can't be claimed" caveat lives in a separate card near the bottom, below the write action in reading order. Plan: move the caveat above or directly beside the write action, not after it. |
| 8 | **`ClaimTag.jsx`'s tag-ID input sits outside its own `<form>`** | The Tag ID `Input` (`required`) is a sibling rendered *before* `<form onSubmit={onSubmit}>` opens. | 9 | **No PWA manifest or service worker — no notification channel exists once a tab is closed** | No `manifest.json`, no service worker anywhere in the repo. Plan: scope as a real feature addition (manifest + service worker + push, or at minimum installable-PWA basics) — bigger than a fix, flagged here rather than folded into a quick pass. |
| 10 | **Round 7's icon-only admin buttons are under typical touch-target size** | `Moderation.jsx`'s `size="icon-sm"` buttons ("View chat"/"Mark reviewed", added in Round 7 to de-crowd the row) render at 32×32px; common guidance (Apple HIG/Material) targets ~44–48px minimum.
